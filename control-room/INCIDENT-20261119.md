# INC-20261119 — 关闭 Chrome 后程序再未恢复：自有 CDP 连接失聪（2026-11-18 17:36 起，持续 32 小时）

**结论：`ROOT_CAUSE_CORRECTED_TO_PROXY_ROUTE / FIXED / INSTALLED_RUNNING / BUSINESS_VERIFIED`。**

- **真实故障不在表格，也不在网络。** 今天实测：同一个 Chrome、同一份表格，用一个**新建的连接**打开只需 2.7 s，网格 0.7 s 就绪，导出菜单能正常产出 TSV。表格一直是好的，Owner 的判断是对的。
- **失效的是程序自己持有的那条连接。** 11-18 17:36 起，每一轮询价/报价/TP 都在**拿到页面之前**失败（`TimeoutError`），被当成"表格暂时不可用"推迟 15 分钟，然后再失败——32 小时、258 次，直到人工重启。程序没有任何自愈路径。
- **原来的提示是错的。** 界面写"表格读取失败…检查网络/VPN"，而 Chrome 网络、表格权限、代理全部正常。这句误导把人和时间都带偏了。

## 4. 第一版判断（**已被第 8 节推翻**，保留以说明取证过程）

Owner 关掉 Chrome 窗口（所有标签页）之后，本轮运行**缓存的 CDP 连接**仍在 `is_connected() == True`，但对页面级命令不再给出任何回答。于是：

1. `_operation_session` 建立会话 → 超时 → 转成 `TimeoutError("GOOGLE_WEB_SESSION_UNAVAILABLE")`；
2. `_temporary_web_read_failure` 把 `TimeoutError` 判为**瞬时读**（这个判断本身是对的：不该停机、不该发技术邮件）；
3. `_defer_website_poll` 推迟 15 分钟，用**同一个坏连接**重试 → 再次失败；
4. `_v13_browser` 只在 `browser.is_connected()` 为 False 时才重连——失聪的连接仍然"已连接"，所以**永远不会重连**。

结果：只要不重启程序，业务就再也不动。这也解释了 258 次完全相同的失败，以及每轮 127–255 s 的耗时（有界重试 × 每次 10 s 连接超时）。

## 5. 第一版的修复（CDP 连接自愈；不是本次根因，但补上了一个真实的健壮性缺口）

- **读取层精确分类**（`src/launcher/google_web.py`）：新增 `_transport_stalled()`，只把"页面/会话命令没有得到回答"（Playwright 截止时间、`GOOGLE_WEB_SESSION_UNAVAILABLE`）判为通道失聪；**站点回答过的错误**（`net::ERR_*` 导出失败、登录页、V12 保护码）**不算**，不会被误当成连接问题。
- **一次轮询最多请求一次重建**：`poll_scope` 重置 `_stall_reported`；`_operation_session` 与读取失败分支都只上报第一次。
- **后端重建自己的连接**（`src/launcher/backend.py::_recover_google_transport`）：丢弃当前 CDP client → 走既有的 `_v13_browser` 重新 attach。**绝不 kill Chrome、绝不换 profile、绝不换端口**（Owner 规则：一个 Chrome、一个 profile、一个 9222）。两条硬边界：① 有 INSO 单据面打开时**不换**（避免打断在途写入）；② 120 秒内最多重建一次。
- **提示改成真话**（`fault_diagnostics` / `workbench`）：新增 `GOOGLE_PAGE_UNRESPONSIVE`——"表格页面通道没有回应（不是表格不可用）"，说明失效的是程序自己的页面连接、常见于 Chrome 窗口被关闭或标签页被重建之后，并给出"程序已自动重连，若连续多轮仍在则重启程序"的可执行建议。同时显示 **发生阶段**（如"连接共享浏览器（google-session）"）。
- **日志可追溯**：`runtime fault` 行新增 `stage=` 与 `chain=`（只含自有点位名与异常类名，不含页面文本）；会话建立失败会打 `workflow step failed at google-session`。

## 8. 真正的根因（21:57 补测，推翻"CDP 连接"假设，如实记录）

第一版修复（把失聪的 CDP 连接重连一次）在 21:47 装上后，**业务仍然失败**。继续逐层取证，得到确定结论：

1. `production.json` 里 `google_api.enabled = true`，源表读取走的是 **Google Sheets API**（`google_reader` + 服务账号），**不是** CDP 页面。所以"关掉 Chrome 影响读表"只是时间上的巧合。
2. 同一条命令实测：
   - 直连：`https://sheets.googleapis.com/` → `curl code=000`（15 s 超时）；Python `WinError 10060`（连接超时）；
   - 走系统代理 `127.0.0.1:7890`：`code=400`（TLS 通，Google 正常应答）；`docs.google.com` → `302`。
3. 原因：`httplib2.Http(timeout=...)` **不带代理**，Chrome 用的是 **Windows 系统代理**。VPN 从 TUN 模式换成"系统代理"模式后，浏览器照样能开表格，程序的 API 连接却直连被墙 → 每轮 30 s 超时 → `GOOGLE_WAITING_RECOVERY`。

这解释了全部现象：表格在浏览器里一直是好的（Owner 判断正确）、程序一次 Google 步骤都没走到（因为不走页面）、换版本/重启都没用（环境问题）、11-18 17:36 之前正常（当时 TUN 生效）。

**修复：**

- `google_api_service`：新增 `system_proxy_address()` + `_proxy_info()`，把 **Windows 系统代理**（HKCU `ProxyEnable`/`ProxyServer`，支持 `host:port` 与按协议列表）交给 `httplib2`；`production.json` 的 `google_api.proxy` 支持 `auto`（默认）/`none`/`http://host:port`。
- 打包：`httplib2` 的 CONNECT 依赖 **PySocks**（缺失时 0.32 会静默超时而不是报错），已装入构建环境并在 `packaging/INSO_V1.1.spec` 里 `hiddenimports += ["socks"]`；已核对 EXE 归档内确实包含 `socks`。
- 文案：`GOOGLE_WAITING_RECOVERY` 现在明说"浏览器能打开表格不等于本程序能连上"，并指向代理/VPN，而不是笼统的"检查网络"。
