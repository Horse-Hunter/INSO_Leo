# RFQ-016 第一阶段（Google API 全面迁移）— 2026-11-13

正在实现什么：
把 Google 表格的读取和写入从“浏览器点表格”改成官方 Sheets API（用已通过真实验证的服务账号），只把表格里那个「更新报价」按钮留在浏览器里，顺手修掉这次迁移会碰到的故障误判。

理想变化是什么：
读表写表不再依赖页面是否漂移、下载是否超时——今天生产日志里绝大多数失败都属于这一类；授权长期有效，不再每七天人工重授权；某个模块的一次读取失败不再拖停整个程序。

以前是什么：
所有读写都走 CDP 原生界面：读=File/Download TSV，写=名称框+公式栏键入。今天 03:32 与 18:33–18:48 两次生产运行里，`write-fragment-drift` 178 次、`read-fragment-drift` 153 次、`download-read` 超时 92 次、`open-sheet` 原生协议超时 14 次，最后以 `CDP_PAGE_CLEANUP_UNCONFIRMED` 收尾。同时 API 的 429/5xx、401/403 完全不在既有“可延迟读取”的词汇表里，一旦换成 API，同样的读取失败会被判成模块暂停甚至全局停止。

现在是什么：
- **一条开发主线、一个默认关闭的开关**。`google_api.enabled`（默认不存在/false）+ `google_api.service_account_file`（仓库外，明文 JSON 或复用现有 DPAPI 加密副本）。开关关着时行为与今天完全一致；打开时读、写走 API，「更新报价」按钮仍走原来的 CDP 动作类。没有第二套 OAuth、项目、调度器、台账或邮件。

以前是什么：
我的上一版用 `UNFORMATTED_VALUE` 只把型号列转成文本——W 列证据里仍留着数字型号，和 A:G 的 `"123"` 对不上，正式读取会报“来源订单日期身份已变”；真实日期会以序列号返回，而 `inquiry_day` 只接受日期/字符串，年龄门槛会全线失效；`RFQ_BRIEF` 的数字字段不满足 `BriefReader` 的“全字符串”要求。写入侧则沿用旧报价流程的重试：超时/回执缺失会被当成普通失败再写四次，5xx/429 还可能升级成全局停止；回执只检查“是不是字符串/整数”，`updatedCells=0` 或写错列也会被判成功；旧的“可写工作表/可写列/14 格范围”限制丢失；W 表头唯一性被放宽。

现在是什么：
